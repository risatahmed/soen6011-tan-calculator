# Problem 3 — How Algorithm A and Algorithm B Differ

| Dimension | Algorithm A (Maclaurin series) | Algorithm B (CORDIC) |
|---|---|---|
| Core technique | Truncated power-series summation for `sin`/`cos`, then divide | Iterative shift-and-add rotation of a 2-D vector by a precomputed angle table |
| Core arithmetic primitives | Real multiplication and division at every term | Only addition, subtraction, and binary shift (`2^-i`) at every iteration |
| Convergence behaviour | Super-linear (factorial-denominator growth) — few terms needed (~10-15 for `1e-12` relative error at `|r| <= pi/4`) | Linear — approximately one bit of precision per iteration (~40 iterations for comparable precision, confirmed in the worked trace: `0.986` after 7 iterations, `1.000000000000` after 39) |
| Termination mechanism | `while` loop bounded by *tolerance met* **or** `N_MAX` term cap, whichever comes first | `for` loop with a fixed, input-independent iteration count `N_MAX` |
| Precomputed constants needed | `PI` (finite-precision constant) | `A[0..N_MAX-1] = arctan(2^-i)` table, and (if `sin`/`cos` individually needed) gain constant `K` — not needed for `tan` alone, since `K` cancels in `vy/vx` |
| Pole handling | Guard on `|cosR| < EPSILON` after the two series are evaluated | Guard on `|den| < EPSILON` after `N_MAX` rotations (same guard shape, different upstream computation) |
| Range-reduction dependency | Requires the shared `mod (pi/2)` reduction to keep the series argument small for fast convergence | Requires the same shared reduction to stay within CORDIC's convergence radius (~1.7433 rad) — reduction step itself is common to both, not a point of difference |
| Implementation effort (D1 prototype, using `math` library) | Low — straightforward translation of the series recurrence | Low-to-moderate — requires generating/storing the `arctan(2^-i)` table (can be done once via `math.atan` in D1's prototype) |
| Suitability for D2 "from scratch" (no built-in `sin`/`cos`) | Needs a from-scratch multiplication and division, and a from-scratch way to obtain a precise `PI` constant | Needs only from-scratch addition/subtraction/shift for the rotation loop itself; the angle table and (optional) gain constant must still be generated by *some* precise method once and stored as constants — but the per-input hot path avoids multiplication/division entirely |
| Performance profile | Fewer operations, but each is a full multiply/divide | More operations, but each is arithmetically trivial (shift/add) — historically preferred in hardware with no multiplier |
| Explainability to the persona (Maya) | Intuitive: "it's the same series you'd Taylor-expand by hand" — easy to explain in a lab-report footnote | Less intuitive: requires explaining vector rotation and a lookup table — harder to explain briefly, though the shift-and-add mechanism has a compelling geometric picture (rotating a vector) |
| Numerical weaknesses shared by both | Argument-reduction error growth for large `|x|`; near-pole precision loss just outside the `EPSILON` band | Same two weaknesses (inherited from the shared reduction step) |
| Numerical weaknesses unique to one | Catastrophic cancellation risk in the reduction subtraction is somewhat more exposed because each series term itself involves subtraction of large intermediate products for large `n` | Ultimate precision capped by the table's precomputed precision/length, independent of runtime tolerance settings |

**Conclusion:** the two algorithms are substantially different along technique, arithmetic primitives, convergence class, and termination mechanism — not superficial variants of a single idea. The choice between them (Problem 4, out of scope for this session) will weigh the low-multiplication profile of CORDIC (attractive for the D2 from-scratch constraint) against the faster per-term convergence and simpler explainability of the Maclaurin series.
